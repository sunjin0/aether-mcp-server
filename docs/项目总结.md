# Aether MCP Server 项目总结

## 1. 项目介绍

`aether-mcp-server` 是 Aether 平台的 Python MCP（Model Context Protocol）工具服务。它向 Deep Agent 提供标准 MCP 工具，并通过 Java Admin 在每次 Agent 运行时签发的短期委派 JWT 实施工具级权限控制。

项目同时包含独立的 Sandbox Runner。Runner 从平台控制面领取已冻结的产物任务，在受资源约束且无网络的 Docker 容器中执行受控运行时或平台通用渲染器，最终将校验后的文件上传回平台。

核心目标如下：

- 以 stdio 与 Streamable HTTP 两种传输方式提供 MCP 服务。
- 支持文档下载、解析、OCR、表格结构提取与 Markdown/JSON 输出。
- 支持受控生成 PDF、DOCX、XLSX 等文件产物。
- 将授权决策集中在 Java 平台，Python 服务只校验和转发短期委派令牌。
- 通过容器隔离、冻结输入、完整性校验和资源限制降低产物任务执行风险。

## 2. 技术栈与框架

| 类别 | 技术 | 作用 |
| --- | --- | --- |
| 语言与构建 | Python 3.11+、uv、Hatchling | 项目运行、依赖解析与构建 |
| MCP 框架 | `mcp` / FastMCP | 工具、资源、提示词注册，以及 stdio 和 Streamable HTTP 传输 |
| Web 运行时 | Uvicorn、Starlette、AnyIO | HTTP 服务、ASGI 中间件、阻塞任务转线程执行 |
| 数据校验 | Pydantic | MCP 输入输出模型及 REST 请求参数校验 |
| 文档解析 | Docling、RapidOCR、PyTorch、Torchvision | PDF、图片及办公文档转换、OCR、表格提取 |
| JWT | PyJWT | Java 委派 JWT 的签名、有效期和声明校验 |
| 容器编排 | Docker、Docker Compose | MCP 服务、Runner 与受控运行时部署 |
| Python 产物渲染 | WeasyPrint、python-docx、openpyxl | PDF、DOCX、XLSX 生成 |
| Node 受控运行时 | Node.js、PDFKit、docx、xlsx、Handlebars | 新协议任务的 Node 脚本运行环境 |
| 测试 | pytest、unittest | MCP 服务与 Runner 行为验证 |

主服务的直接生产依赖定义在 `pyproject.toml` 中；沙箱产物渲染依赖被固定在 `sandbox-runtime/python.Dockerfile` 和 `sandbox-runtime/node.Dockerfile`，以保证不同任务执行时的渲染行为可复现。

## 3. 代码结构

```text
src/aether_mcp_server/
  __main__.py       命令行入口，启动 stdio/HTTP 服务或预下载模型
  server.py         FastMCP 注册、REST 路由、HTTP 鉴权中间件
  tools.py          消息、时间与 Docling 文档处理工具
  artifact.py       受控产物任务提交客户端
  auth.py           Java 委派 JWT 校验器
  idempotency.py    有副作用工具的进程内幂等缓存
  resources.py      MCP 示例资源
  prompts.py        MCP 示例提示词

sandbox-runner/
  runner.py             控制面任务领取、容器生命周期与结果回传
  generic_artifact.py   平台维护的 PDF/DOCX/XLSX 通用渲染器
  Dockerfile            仅含 Docker CLI 与 Python 标准库的 Runner 镜像

sandbox-runtime/
  python.Dockerfile     固定版本的 Python 受控运行时
  node.Dockerfile       固定版本的 Node 受控运行时

tests/                   MCP 服务、鉴权、幂等、文档处理与 Runner 测试
docs/                    项目文档
```

## 4. 对外能力

### 4.1 MCP 工具

| 工具名 | 说明 | 主要输入 | 输出 |
| --- | --- | --- | --- |
| `echo_message` | 原样回显消息 | `message` | `message` |
| `get_current_time` | 获取当前 UTC 时间 | 无 | ISO 8601 `timestamp` |
| `process_document` | 下载或读取文档并交给 Docling 转换 | `source`、`output_format`、`ocr`、`extract_tables` | Markdown、JSON 文档结构、页数等元数据 |
| `generate_artifact` | 向平台申请受控文件生成任务 | `title`、`content`、`format`、可选文件名和文档计划 | 平台执行 ID、运行 ID、任务状态 |

其中 `process_document` 支持 `markdown`、`json`、`both` 三种输出模式。PDF 与图片共用 Docling 的版面/OCR 管线，`ocr` 和 `extract_tables` 参数分别控制 OCR 和表格结构识别。

`generate_artifact` 只接受已授权的内容和格式，不允许 Agent 自行选择镜像、模板或任意命令。当前通用渲染器支持：

- DOCX：处理 Markdown 标题、列表和表格。
- XLSX：读取结构化 `document.sheets`；未提供时尝试从 Markdown 表格或文本生成单工作表。
- PDF：支持受限 Markdown；检测到 HTML 时先执行标签、样式和链接白名单清洗，再离线渲染。

### 4.2 REST 接口

在 HTTP 模式下，除 MCP 端点 `/mcp` 外还提供下列接口：

| 接口 | 用途 | 鉴权要求 |
| --- | --- | --- |
| `POST /api/process-document` | 使用 JSON 请求体处理 URL 文档 | 启用 `--auth` 时需要 `process_document` 权限 |
| `POST /api/convert-file` | 接收 multipart 文件上传并转换 | 启用 `--auth` 时需要 `process_document` 权限 |
| `GET /health` | 健康检查，返回 `{"status":"ok"}` | 无额外校验 |
| `GET /metrics` | 返回进程内幂等命中、提交和缓存数量 | 无额外校验 |

## 5. 架构与处理流程

### 5.1 HTTP MCP 调用链

```text
Deep Agent / Java MCP 执行器
        |
        | Bearer 委派 JWT
        v
Aether MCP Server (FastMCP + Uvicorn)
        |
        | DelegatedToolScopeMiddleware
        | 校验签名、过期时间和 allowedTools
        v
MCP 工具
        |-- echo_message / get_current_time
        |-- process_document -> Docling
        `-- generate_artifact -> Java Admin 内部接口
```

HTTP 模式使用 `DelegatedToolScopeMiddleware` 在 ASGI 最外层读取 JSON-RPC `tools/call` 请求。中间件根据 `Authorization: Bearer <JWT>` 验证令牌，并确认调用工具存在于 `allowedTools` 中。验证通过后，令牌被保存到 `ContextVar`，供异步工作任务中的 `generate_artifact` 使用。

工具发现请求，例如 `initialize`、`ping`、`tools/list`，不由该中间件要求工具委派权限；工具实际调用则必须通过范围校验。FastMCP 同时启用 DNS 重绑定保护，并限制可接受的 Host。

### 5.2 文档处理流程

```text
URL 或上传文件
  -> 本机文件 URL 改写为 Docker 内部 Admin 地址（如适用）
  -> 内网 HTTP 地址下载到临时文件
  -> Docling DocumentConverter
  -> Markdown 和/或 JSON 结构
  -> 返回页数等元数据
  -> 删除本次创建的临时文件
```

当浏览器传入 `localhost`、`127.0.0.1` 或 `::1` 上的 `/api/file/` 地址时，服务会使用 `AETHER_ADMIN_INTERNAL_URL` 替换主机部分，以便容器能够访问管理端服务。解析为私网、回环或链路本地地址的 HTTP URL 会先下载到临时文件，再交由 Docling 读取。

### 5.3 产物生成与沙箱流程

```text
generate_artifact
  -> Java Admin 创建冻结产物执行任务
  -> Sandbox Runner 轮询并领取任务
  -> 校验任务、资源名称、SHA-256、输入工件元数据
  -> 创建 resources / input / output 三个 Docker volume
  -> 启动无网络、只读、低权限的任务容器
  -> 校验输出数量、扩展名、大小和校验和
  -> 上报用量、上传产物或失败原因
  -> 删除容器与临时 volume
```

Runner 优先领取新版 `/api/agent/sandbox/runner/claim` 任务，未领取到时兼容旧版领取接口。新版任务可执行由平台冻结的 Python/Node 脚本槽位，或固定命令模板；通用产物任务使用 `generic_artifact.py`，不执行 Agent 提供的代码。

## 6. 安全设计

### 6.1 委派鉴权

- Java Admin 是唯一授权决策方，负责签发短期 JWT。
- JWT 必须包含 `exp`、`runId`、`userId`、`agentId`，并使用 `allowedTools` 约束调用范围。
- Python 服务使用 `AETHER_MCP_DELEGATION_SECRET` 以 HS256 校验签名，不维护静态 Token 白名单。
- `generate_artifact` 只使用显式传入或 HTTP 中间件已经验证的委派令牌，缺少令牌即拒绝执行。

### 6.2 幂等控制

`generate_artifact` 可能触发平台侧任务提交，因此使用进程内 `IdempotencyStore` 防止同一运行的重复调用。缓存键由 `runId`、工具名和经排序序列化的参数计算而来；同一运行内相同参数的重试直接返回原确认结果。

该缓存最大保存 10,000 个操作，按插入顺序淘汰最旧记录。它只覆盖单个 Python 服务进程的生命周期；服务重启后的恢复由 Deep Agent 的检查点和 outbox 机制负责。

### 6.3 沙箱隔离

任务容器的关键限制包括：

- `--network none`，禁止网络访问。
- `--read-only`，根文件系统只读。
- `--cap-drop ALL` 与 `no-new-privileges`，移除 Linux capabilities 并阻止权限提升。
- 非 root 用户 `10001:10001` 执行任务。
- 限制 PID、内存、CPU 与 `/tmp` 大小。
- resources 和 input volume 只读挂载，只有 output volume 可写。
- Runner 自身才拥有 Docker socket；任务容器不拥有 Docker 引擎访问能力。

Runner 还会验证资源及输入文件的 SHA-256、文件名是否包含目录穿越、允许的输出格式、输出数量和最大字节数。执行过程中通过心跳续租并响应平台取消请求；超时或取消时会终止对应容器。

### 6.4 HTML 与文件渲染安全

通用 PDF 渲染器对 Agent 提供的 HTML 使用白名单策略：

- 仅保留布局相关标签。
- 丢弃脚本、样式表、iframe、表单、媒体与其他主动内容。
- 仅允许有限 CSS 属性，拒绝 `url()`、`@import`、`javascript:` 等危险值。
- 链接仅允许 HTTP/HTTPS。
- 原始 Markdown 会先 HTML 转义，再由渲染器生成受控标签。

## 7. 运行与部署

### 7.1 本地开发

前置条件：Python 3.11+ 与 `uv`。

```powershell
uv sync

# 默认 stdio MCP 传输
uv run aether-mcp-server

# Streamable HTTP，默认监听 127.0.0.1:8000
uv run aether-mcp-server http --host 127.0.0.1 --port 8000

# 预下载核心 Docling 模型，减少首次调用等待时间
uv run aether-mcp-server download-models
```

生产 HTTP 服务应启用认证：

```powershell
$env:AETHER_MCP_DELEGATION_SECRET = "replace-with-a-long-random-secret"
uv run aether-mcp-server http --auth --host 0.0.0.0 --port 8000
```

未使用 `--auth` 的 HTTP 模式仅适合本地调试。stdio 模式不使用 HTTP Bearer 鉴权。

### 7.2 Docker Compose

```powershell
# 构建并启动 MCP 服务
docker compose up -d --build aether-mcp

# 构建 Python/Node 受控运行时和 Runner
docker compose --profile build build sandbox-runtime-python sandbox-runtime-node sandbox-runner

# 启动 Runner
docker compose up -d sandbox-runner
```

Compose 会将 Hugging Face 和 Docling 缓存持久化到具名 volume，以避免重复下载模型。

### 7.3 主要环境变量

| 变量 | 用途 |
| --- | --- |
| `AETHER_MCP_DELEGATION_SECRET` | Java 与 MCP 服务共享的 JWT 验签密钥 |
| `AETHER_ADMIN_INTERNAL_URL` | Docker 网络内 Java Admin 服务地址，默认 `http://aether-admin:8080` |
| `HF_ENDPOINT` | Hugging Face 模型下载地址或镜像地址 |
| `AETHER_SANDBOX_RUNNER_TOKEN` | Runner 调用控制面接口的身份令牌 |
| `AETHER_SANDBOX_RUNNER_ID` | Runner 实例标识，默认使用主机名 |
| `AETHER_SANDBOX_POLL_SECONDS` | 任务轮询间隔，默认 2 秒 |
| `AETHER_SANDBOX_PYTHON_IMAGE` | Python 沙箱运行时镜像 |
| `AETHER_SANDBOX_NODE_IMAGE` | Node 沙箱运行时镜像 |
| `AETHER_SANDBOX_ALLOWED_IMAGE_DIGESTS` | 新协议模板允许使用的摘要固定镜像集合 |

## 8. 测试与质量保障

测试位于 `tests/`，覆盖以下领域：

- 命令行启动参数与 HTTP/stdio 行为。
- Java JWT 鉴权、工具范围限制和 REST 接口保护。
- Docling 文档处理参数、内网 URL 改写和临时文件清理。
- 通用产物 HTML 清洗、Markdown 标题去重和文件渲染逻辑。
- 运行内幂等键、缓存淘汰和重复提交保护。
- Sandbox Runner 的任务校验、超时、取消、用量上报和多产物回传。

建议使用以下命令执行测试：

```powershell
uv run pytest -v
```

## 9. 当前边界

- 文档处理实现主要针对 URL 与上传文件；支持的具体格式由已安装的 Docling 能力决定。
- 幂等缓存是进程内状态，不是跨进程或跨重启的持久化去重机制。
- `generate_artifact` 的执行队列、产物持久化和最终授权仍属于 Java Admin 控制面职责。
- Runner 虽然因管理容器生命周期而挂载 Docker socket，但实际任务容器不会获得该 socket，也没有网络权限。
- `WEB_COLLECTION` 任务在当前 Runner 中会直接拒绝，只有配置专用出网代理 Runner 后才可支持。
